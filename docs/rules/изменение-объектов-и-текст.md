# Изменение объектов и проверка текста

Проверки входят в `make layout-check`, а через него — в `make precommit`.
Хук precommit запускается и при изменении одних документов.

## Кто может присваивать значения

| Где создан объект | Кто может присваивать поля и элементы |
|---|---|
| Юзкейс | Этот же юзкейс |
| Сервис домена или application | Этот же сервис и юзкейс |
| Инфраструктурный сервис, в том числе результат порта | Этот же сервис и юзкейс |

Сервис здесь определяется классом, а не отдельным методом. Юзкейс определяется
каталогом `use_cases_dir` в `[tool.code_layout]`. В этом проекте единственный
публичный метод юзкейса — `execute`, что проверяет `check_use_cases.py`.
`__init__` может присваивать собственные поля для сохранения зависимостей.

`scripts/check_object_ownership.py` проверяет `obj.field = value`,
`obj[key] = value`, составные присваивания и вызовы
`dataclasses.replace`/`copy.replace`, включая импорт с другим именем.
Обычный `str.replace` под этот запрет не попадает.
Присваивание второго имени `other = obj` не создаёт нового объекта.
Передача и возврат через несколько функций не меняют владельца.
Вызовы портов определяются по типу зависимости из `application/ports`
или объявлению `Protocol`; их результат получает инфраструктурное происхождение.

Например, application-сервис может получить пользователя через репозиторий
и вернуть его юзкейсу, но не может присвоить ему имя:

```python
async def load(self, user_id: int) -> User:
    user = await self._users.get_by_id(user_id)
    return user
```

Юзкейс может присвоить `user.name = name` после этого вызова.

Проверка анализирует исходники без запуска приложения. Она использует явные
импорты, типы зависимостей и поток значений. Ветвления объединяют возможные
источники: разрешение должно быть у всех вариантов. Неизвестное происхождение
при попытке присваивания даёт ошибку. Ошибка разбора и пустой каталог также
не считаются успешной проверкой.

Пределы: это не доказательство поведения произвольной программы Python.
Динамический импорт, рефлексия и идентичность экземпляров одного класса не
моделируются. Вызовы обычных методов не классифицируются как изменение:
`append`, `update` и пользовательские методы не входят в это правило.
Проверяются именно явные присваивания в исходниках и указанные функции `replace`.

## Специальные методы и isinstance

`scripts/check_explicit_state.py` запрещает определения `__имя__` во всём
`app/`, кроме `__init__`. Чтение `handler.__name__` остаётся разрешённым.
Методы, автоматически созданные `dataclass` или внешней библиотекой, не
являются определениями в исходниках `app/` и под запрет не попадают.

В `application`, `composition`, `domain` запрещён вызов `isinstance`,
включая импорт из `builtins` под другим именем. Список слоёв находится в
`[tool.explicit_state].isinstance_layers`. В инфраструктуре вызов разрешён.
Маршрутизаторы композиции используют сопоставление `match` с образцом события.

## Кодировка документов и комментариев

`scripts/check_text_encoding.py` читает текстовые исходники, Markdown, RST,
TXT, конфигурацию, шаблоны и Makefile как UTF-8. Проверяются целые файлы,
поэтому комментарии, докстроки и обычные строки тоже попадают в проверку.
Нормальная кириллица и другие языки разрешены.

Некорректный UTF-8, символ замены Unicode и посторонние управляющие символы
дают ошибку с путём и строкой. Дополнительно проверяются обратимые следы
ошибочного чтения UTF-8 как Windows-1251, Windows-1252 и Latin-1.
Это эвристика: она не обнаруживает все возможные повреждения текста.
Файлы автоматически не переписываются.

Список файлов берётся из Git тем же способом, что и для кэша precommit:
отслеживаемые файлы плюс новые неигнорируемые. Отдельного списка исключений
нет: действуют `.gitignore`, вложенные правила и отмена исключений через `!`.
Отслеживаемый файл проверяется даже при наличии подходящего исключения.
Удалённые файлы, ссылки и двоичные форматы не сканируются.
PDF и документы Office эта проверка не разбирает. Для запуска нужен Git.
