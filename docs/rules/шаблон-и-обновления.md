# Шаблон и обновления

Как проект заводится из шаблона и как потом забирает его правки.

Правило переносимое: про любой шаблон, из которого растут проекты. Здесь оно
описано целиком; в CLAUDE.md — только ссылка и две команды.

---

## Как это устроено

Адрес шаблона и ветка лежат в `pyproject.toml` проекта:

```toml
[tool.template]
url = "https://github.com/user/ddd-fastapi-template"
ref = "master"
name = "ddd-fastapi-template"
manual = ["migrations/versions", "app"]   # конфликт здесь решает человек
alert = ["migrations/versions"]           # опасно даже без конфликта
```

**Git-remote для шаблона не заводится.** `git fetch <url> <ref>` умеет работать
по адресу напрямую, складывая результат в `FETCH_HEAD`. Отдельный remote был бы
вторым местом хранения того же адреса — и однажды они разошлись бы: конфиг
говорит одно, `.git/config` другое, обновления идут не оттуда, и никакой ошибки
при этом нет.

`url` приезжает вместе с шаблоном уже заполненным — это адрес самого шаблона,
записанный в шаблоне, и ошибиться в нём неоткуда. Вычислять его из `origin`
нельзя: порядок действий у всех разный, и тот, кто сначала переставил `origin`
на свой репозиторий, записал бы туда **собственный** адрес. Дальше проект
«обновлялся» бы сам из себя — молча и всегда успешно.

`name` — имя, под которым шаблон приезжает. `make init` меняет
`[tool.poetry].name`, а это поле не трогает: их несовпадение и есть признак,
что проект отвязан.

## Новый проект

```bash
git clone https://github.com/user/ddd-fastapi-template myproject
cd myproject
make init NAME=myproject
```

`make init` подставляет имя в `pyproject.toml` и `README.md`, а `origin`
удаляет — но **только если тот указывает на шаблон**. Смысл в том, чтобы код
проекта нельзя было случайно запушить в шаблон. Свой `origin` вы заводите сами,
когда репозиторий появится.

**Коммит `init` не делает.** Правки остаются в рабочем дереве, чтобы вы увидели
дифф и согласились с ним, а не обнаружили постфактум.

Дальше обычный старт: `make install`, `make infra-up`, `make migrate`.

### Пропустить `init` не получится

`scripts/check_not_initialised.py` входит в `lint-check`, то есть срабатывает и
в `make check`, и в `make precommit`. Пока имя проекта совпадает с именем
шаблона — отказ.

Проверка нужна не против забывчивости, а против молчания: README можно не
прочитать, а красную проверку — нет.

### Если вы дорабатываете сам шаблон

Отличить шаблон от его свежего клона по содержимому **невозможно** — деревья
байт в байт одинаковы, и `origin` у них один и тот же. Поэтому признак живёт
вне git:

```bash
touch .is-template
```

Файл в `.gitignore`, в проекты не уезжает, заводится один раз на машину. Он же
работает и в обратную сторону: `make init`, запущенный в самом шаблоне, увидит
маркер и откажется — переименовывать шаблон в проект нечего.

## Существующий проект: прививка

У проекта, который начинался не из шаблона, история с ним не общая, и обычное
слияние дало бы конфликт почти в каждом файле.

```bash
# 1. выровнять общее руками: scripts/, .claude/, docs/rules/, цели Makefile
git commit -am "выравнивание с шаблоном"

# 2. записать адрес шаблона в pyproject.toml, секция [tool.template]

# 3. привить, ничего не забирая
make template-graft
```

Прививка — это `git merge -s ours --allow-unrelated-histories`: коммит слияния
с вашим деревом и записанным родителем из шаблона. Дерево не меняется ни на
байт; меняется только то, от какой точки git считает дельту. Дальше проект
обновляется как любой другой.

Шаг 1 автоматизировать нельзя: какие из ваших файлов «те же самые, что в
шаблоне», знаете только вы.

## Обновление

```bash
make template-diff      # что придёт и во что обойдётся — ничего не меняет
make template-update    # слить в ветку-буфер
```

### `template-diff` показывает три вещи

**Что придёт** — коммиты и файлы, которых у вас ещё нет.

**Насколько разошлись** — сколько коммитов с каждой стороны. Число слева растёт
с жизнью проекта и само по себе не тревожно; тревожно, когда оно большое, а
общих правок много.

**Конфликты — предсказанием, а не гаданием.** `git merge-tree` проигрывает
слияние в памяти и называет конфликтующие файлы поимённо, не трогая рабочее
дерево. То есть цена обновления известна до того, как вы за него взялись.

### `template-update` сливает в ветку-буфер

Отказывает, если в дереве есть незакоммиченное: разбирать конфликты поверх
собственных недоделок — верный способ потерять и то и другое. И зависит от
`make check`: в красное дерево не сливаем, иначе после слияния не разобрать,
чья краснота.

Слияние идёт в ветку `template-update`, а не в рабочую. Не понравилось —
`git branch -D template-update`, и основная ветка ничего не заметила. Дожали —
слили буфер в себя обычным `git merge`.

### Что нельзя разрешать самому

Конфликты в путях из `[tool.template].manual` агент обязан вынести человеку, а
не решать:

**`migrations/versions/`** — у шаблона своя цепочка ревизий, у проекта своя.
Слитые вместе, они дают две головы, и `alembic upgrade head` перестаёт
работать. Лечится перенумерацией и переуказанием `down_revision` — решение о
том, какая ревизия за какой, принимает человек.

**`app/**`** — это ваш код. Совпадение путей ещё не значит, что шаблонная
версия чем-то лучше вашей; чаще наоборот.

Остальное (`pyproject.toml`, `Makefile`, `CLAUDE.md`) обычно дописывание в
списки и разбирается механически.

### И отдельно — то, что опасно БЕЗ конфликта

Новая миграция из шаблона не конфликтует ни с чем: файл новый, спорить не с
чем, слияние проходит чисто. И ровно поэтому она опаснее конфликта — отчёт
«конфликтов не будет» формально прав, а `alembic upgrade head` после такого
слияния не работает: голов в цепочке стало две.

Такие пути перечислены отдельным ключом `[tool.template].alert`, и обе команды
показывают их своим блоком. `template-update` в этом случае возвращает
ненулевой код **даже при успешном слиянии** — не потому, что слияние не
удалось, а потому, что пускать его дальше, пока цепочку не разобрал человек,
нельзя.

Отчёт при этом — предупреждение, а не преграда: его можно не прочитать.
Преграду держит `scripts/check_migration_heads.py` в `lint-check`: он считает
головы у цепочки ревизий и отказывает, пока их больше одной. То есть даже
слияние, сделанное мимо этих команд — руками, из IDE, из чужой ветки, — упрётся
в красный `make check`, а не в падение выкладки у следующего.

Ключей два, потому что и опасности две: `manual` — «спорное содержимое, выбор
за человеком», `alert` — «бесспорное содержимое, но ломает то, чего в диффе не
видно».

## Со стороны шаблона

Правка общего рождается в шаблоне и едет вниз; обратного потока нет. Поэтому:

- **демо трогают редко.** Проект, удаливший демонстрационную сущность, получает
  конфликт «изменено/удалено» на каждую её правку;
- **миграции после первоначального набора не добавляют** — либо добавляют и
  тогда пишут в описании выпуска, что проектам придётся перенумеровать;
- если проектов станет много и `ref = "master"` начнёт приносить полуготовые
  состояния — заводятся теги, и проекты пиннятся на них. Поле `ref` принимает
  ветку, тег и хэш одинаково, менять код для этого не придётся.
