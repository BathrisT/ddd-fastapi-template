# CLAUDE.md

Инструкция для Claude Code при работе с проектом.
Читается при каждом запуске. Краткий и конкретный.

> **Отступления от правил:** если есть обоснованное отступление — агент **обязан явно сообщить**
> пользователю и объяснить причину. Примеры допустимых: `Any` в протоколах фреймворка,
> `# ruff: noqa` при циклических импортах SQLAlchemy.

---

## Команды

```bash
make precommit        # перед коммитом: lint-check + typecheck + layers + schema-check + тесты + bandit
                      # schema-check требует Docker (сверяет ORM с миграциями)
make check            # быстрая проверка: lint-check + typecheck + layers + unit-тесты
make layout-check     # раскладка кода: где что лежит и какого размера
make interface-check  # слой входа: что в routes/, откуда зависимости
make lint             # ruff check --fix + format
make typecheck        # mypy
make layers           # tach check — проверка зависимостей между слоями DDD
make layers-show      # tach show --web — граф зависимостей в браузере
make layers-report    # tach report <module> — детали по конкретному модулю
make test             # все тесты с coverage
make test-unit        # unit-тесты (параллельно, без Docker)
make test-integration # integration-тесты (поднимает PostgreSQL через testcontainers)
make migrate          # alembic upgrade head
make infra-up         # локальные postgres + redis в docker
make api / worker / scheduler   # запуск точки входа с хоста

# Одиночный тест:
poetry run pytest tests/unit/path/to/test.py::test_name -v
```

## Золотые правила

1. **Провал тестов/линтера = стоп.** Исправляй до зелёного состояния перед продолжением.
2. **Все `.py` файлы проекта живут внутри `app/`.** В корне `.py` файлов быть не должно.
3. **Один файл — одна логическая группа.** Не складывать всё в один файл (например, все ORM-модели).
4. **Репозитории возвращают доменные модели** (`app/domain/models/`), не ORM-объекты.
5. **Не угадывай.** Нет спецификации — уточни у пользователя или создай `docs/`.
6. **Безопасность по умолчанию.** Нет секретов в коде, параметризованные запросы, валидация на границе.

## Раскладка кода

1. **В `app/` нет функций уровня модуля.** Логика принадлежит классу — сущности,
   сервису или утилите со `@staticmethod`. Функция, лежащая рядом с классом, не
   принадлежит никому: на месте вызова видно только имя, а рядом с ней молча
   заводятся дубли.
   Исключение одно и по одной причине — **имя функции требует фреймворк**
   (FastAPI-хендлер, фабрика `Depends`, обработчик очереди). Список путей —
   `module_functions_allowed` в `[tool.code_layout]`; инлайновой пометки-побега
   намеренно нет: единственный способ завести исключение — дописать путь в
   конфиг, и это видно в ревью. Проверяется только `app/`, поэтому
   `upgrade`/`downgrade` в `migrations/` и pytest-фикстуры под правило не
   попадают и в конфиге их нет.
   Проверяется `scripts/check_module_functions.py`.

2. **Файл не длиннее 300 строк** (`max_lines` в том же конфиге). Класс на 88
   методов — та же помойка, что модуль на 88 функций; форму ловит правило 1,
   объём — только лимит.
   Проверяется `scripts/check_file_length.py`.

3. **Подпапка слоя называет роль, а не предметную область.** Предметная область
   живёт уровнем ниже, внутри роли: `dto/messaging/`, а не `messaging/` рядом с
   `dto`. Для `domain` и `application` набор ролей закрыт и перечислен в
   конфиге; у `infrastructure` и `interface` ось другая — «к чему адаптируемся»
   и «по какому протоколу входим». Имена `utils`, `helpers`, `common`, `misc`,
   `shared`, `core`, `lib` запрещены: они не называют ничего.
   Проверяется `scripts/check_layer_folders.py`.

4. **Один класс с поведением на файл.** Носители данных (`@dataclass`,
   pydantic-модели, енумы, `TypedDict`, `Protocol`, исключения, ORM-модели,
   примеси) в счёт не идут: тридцать схем в `schemas/portal.py` — норма, пять
   use case'ов в одном файле — нет.
   Проверяется `scripts/check_class_shape.py`.

5. **Порт или секрет не может быть аргументом `@staticmethod`.** У статического
   метода нет `self`, держать зависимость негде — и её начинают передавать на
   каждый вызов. Верный признак беды: место вызова само прибивает первые
   аргументы через `partial`, то есть руками изображает конструктор. Порт и
   секрет идут в `__init__`, объект собирается в deps. У обычных методов порт
   аргументом бывает законен (скоупнутый на запрос репозиторий) — правило их
   не трогает. Тем же скриптом.

6. **`class X(Protocol)` в `application`/`domain` живёт только в
   `application/ports/`.** Инфраструктура и интерфейс — адаптеры, шов между их
   собственными классами это их дело.
   Проверяется `scripts/check_layer_folders.py`.

7. **Правило бизнеса не размножается константами.** Одно значение, заданное
   модульными константами в пяти и более файлах, — это скопированное правило.
   Место общих правил — `domain/catalog/policy.py`; технические константы
   (TTL локов, лимиты размера) остаются по месту.
   Проверяется `scripts/check_duplicated_constants.py`.
   Отличить правило от техники синтаксически нельзя, поэтому в ревью работает
   вопрос: **если это правило поменяется, сколько файлов я открою?**

8. **Не больше 15 файлов в каталоге** — иначе разбей на подмодули по смыслу.
   Ключ `max_files_per_dir` в конфиге, проверяется
   `scripts/check_layer_folders.py`.

9. **В `application/use_cases/` один файл — один сценарий: класс `*UseCase`
   с единственным публичным методом `execute`.** Носители данных
   (`@dataclass`-команды, енумы) рядом не в счёт. Второй публичный метод —
   это второй сценарий: класс, держащий `confirm`/`reject`/`extend` вместе
   только потому, что у них общие зависимости, прячет от места вызова, сколько
   там на самом деле действий. Общие зависимости — повод завести сервис, а не
   повод склеить сценарии.
   Не-сценарии (валидации, сборщики клавиатур, мосты между шагами) живут в
   `application/services/`, а результаты — в `application/dto/`.
   Проверяется `scripts/check_use_cases.py`.

   **Чужой сценарий не коммитят: один `commit()` на вход.** Класс, получивший
   `*UseCase` в зависимости, не зовёт `commit()` сам — сессия одна на вход, и
   он зафиксировал бы чужую недоделанную работу, а следом ушло бы событие,
   отозвать которое нечем. Держать чужой сценарий при этом законно: диспетчер
   (один сценарий из N) и перечислитель (сценарий на каждый элемент) своих
   записей не делают. По той же причине вход просит не больше одного
   `FromDishka[*UseCase]`. Тем же скриптом.

## Слой входа HTTP (`make interface-check`)

Отдельный набор от раскладки: он не про размер и место файлов, а про то, что
имеет право лежать во входе и откуда хендлер берёт зависимости.

10. **Каждый `.py` в `routes/` объявляет хотя бы один маршрут** (`@router.get`
    и т.п.). Кроме `__init__.py` — агрегаторы собирают роутеры через
    `include_router`, своих маршрутов у них нет.
    Правило нарочно белое, а не чёрное: запрет «в routes не должно быть
    классов» ловит ровно классы, а завтра туда положат функцию-помощника или
    разбор тела — и запрет промолчит. Требование «объявляй маршруты» ловит
    любого чужака сразу.
    Схемы запроса и ответа под правило не попадают: pydantic-модель рядом со
    своим маршрутом читается лучше, чем через две папки, и описывает тот же
    маршрут. Уезжать в `schemas/` им стоит тогда, когда они понадобились двум
    роутерам сразу.
    Проверяется `scripts/check_fastapi_routes.py`.

11. **Роли слоя входа.** `routes/` — только эндпоинты; `schemas/` — формы
    запроса и ответа; `guards/` — проверки, кем представляется запрос;
    `parsing/` — разбор проводного формата в понятные значения. Логике места
    ни в одной из них нет, она в `application/`.
    Каталога `deps/` нет: сборка живёт в `composition/`, а `Depends`
    остаётся только у гейтов входа — проверяется `scripts/check_composition.py`.

12. **Агрегатор называет каждого соседа по пакету.** Файл, которого нет в
    `__init__.py`, не поднимется — и это будет не ошибкой сборки, а
    отсутствием ручки в проде. Как именно включать, правило не диктует: в
    `routes/` бывает два роутера с разными гейтами в одном файле, и требование
    единообразия запретило бы ровно то место, где принимается решение о
    доступе. Импорт при этом резолвится в путь, а не сверяется по последнему
    сегменту.
    Проверяется `scripts/check_package_coverage.py`, конфиг —
    `[tool.package_coverage]`.

13. **Точка входа названа своим реестром.** Обработчик очереди, не попавший в
    `composition/worker_tasks.py`, не падает — он просто не существует для
    отправителя, и сообщение с его именем теряется молча. Правило переносимое:
    «каталог входов → файл, который обязан их назвать», пары в
    `[tool.entrypoint_registry]`; форму записи в реестре не навязываем, вопрос
    один — названо или забыто.
    Проверяется `scripts/check_entrypoint_registry.py`.

## Композиция и скоупы

Правило целиком — [`docs/правила/композиция-и-скоупы.md`](docs/правила/композиция-и-скоупы.md).
Оно переносимое: про приложения с несколькими входами. Коротко:

- **Скоупа два.** Процессный (пулы, настройки, шифры) и привходовой (сессия,
  арендатор, репозитории, авторизованные клиенты). Процессный объект **не имеет
  права держать состояние арендатора** — нарушение не даёт ошибки, оно даёт
  данные одного арендатора другому.
- **Арендатор ставится на границе и ниже только читается**, никогда не
  выводится заново.
- **Проверка транспортная, резолюция общая.** Один резолвер, перебирающий
  способы проверки, запрещён: вход начнёт принимать чужое доказательство.
- **Композиция в одном модуле**, который не принадлежит ни одному входу.
  Контейнер не передаётся аргументом.
- **Вход — это протокол, а не библиотека.** Обработчики очереди лежат рядом с
  HTTP-хендлерами, в `interface/`, а не в инфраструктуре.
- **Регистрация обработчика — явная операция**, а не побочный эффект импорта:
  реестр `composition/worker_tasks.py`, имя задачи — имя функции-обработчика.

Сборка — dishka: `AppContainer.build(settings, broker, *провайдеры входа)`.
Зависимости хендлера объявляются `FromDishka[T]`, `Depends` остаётся только у
верификаторов входа.

Проверяется: пункт про импорт инфраструктуры — `tach`, `Depends` вне
верификаторов — `scripts/check_composition.py` (в `make interface-check`).

## Архитектура

Направление зависимостей: `interface → application → domain`.
Infrastructure реализует порты из application.

| Слой | Путь | Что содержит |
|---|---|---|
| **domain** | `app/domain/` | dataclass-сущности, enums, исключения, доменные события |
| **application** | `app/application/` | use cases, DTO, порты (Protocol) в `ports/` |
| **infrastructure** | `app/infrastructure/` | ORM, репозитории, Redis, брокер очереди, внешние клиенты |
| **interface** | `app/interface/` | ВСЕ входы: `api/` (маршруты, схемы, гейты, разбор) и `worker/` (обработчики очереди, расписание) |
| **composition** | `app/composition/` | сборка графа, реестр задач, маршрутизатор событий; импортируют только точки входа |

**Запрещённые импорты:**
- `domain` — не импортирует FastAPI, SQLAlchemy, taskiq, pydantic-settings
- `application` — не импортирует FastAPI, taskiq, ORM-модели, `AsyncSession` напрямую

## Идентификаторы

- У доменной сущности **`id: int`, и `0` значит «ещё не сохранён»**. Значения
  по умолчанию у поля нет: заводя сущность, автор говорит `id=0` вслух, иначе
  несохранённое и сохранённое выглядят на месте вызова одинаково.
- **Развилку «вставить или обновить» держит репозиторий**, и только он:
  `if entity.id == 0` → вставка, иначе чтение и обновление. Разъедься она по
  сценариям — каждый начнёт решать по-своему.
- **Дальше работают с ВОЗВРАЩЁННЫМ объектом**, а не с переданным: идентификатор
  присваивает база, и у аргумента он так и остаётся нулевым. Событие или задача
  с `id=0` не падает на месте — она уходит в никуда, а обработчик пишет
  «сущности 0 больше нет».

## Время

- **Момент** («когда случилось») — всегда `timestamptz` и aware:
  `datetime.now(tz=timezone.utc)`. Абсолютен, зона ему не нужна. Наивное время
  запрещено правилом `DTZ` в ruff: оно разбирает вызов, а не строку, поэтому
  ловит и `datetime.utcnow()`, и безтайзонный `datetime(...)`.
- **Календарный день** («до какого числа») — `Date`. Зоны у даты нет по
  определению, но вопрос «какое сегодня число» зависит от зоны того, для кого
  считаем.
- Как только у арендатора (портала, компании, пользователя) появляется своя
  зона, «сегодня» перестаёт быть свойством контейнера: заводится объект-часы,
  построенный из этой зоны, и `date.today()` вместе с `.date()` от момента из
  базы запрещаются грепом — `timestamptz` приходит из БД в UTC, и у арендатора
  восточнее UTC утреннее событие попадёт во «вчера». В ветке `multitenant`
  этот кусок уже собран.

## Транзакции

- `AsyncSession` создаётся КОНТЕЙНЕРОМ (`RequestProvider.session`), одна на вход —
  и для HTTP, и для задачи очереди.
- Репозитории получают session снаружи — не создают сами.
- Use case получает репозитории + `Committer`. **Не получает `AsyncSession` напрямую.**
- Один `commit()` в конце use case. `rollback()` — на границе при ошибке.
- **Сессию открывает только её владелец, SQL пишет только репозиторий.**
  У сессии есть хозяин: контейнер открывает её на вход и закрывает вместе с
  ним. Объект, открывающий сессию сам, решает за сценарий, что и когда
  зафиксировано, — а `commit()` в чужой сессии фиксирует заодно всё, что
  сценарий фиксировать не собирался. Записи, которые обязаны пережить
  транзакцию сценария (журнал доставки, выданный внешней системой
  идентификатор), идут через `AutonomousSession` — своя короткая транзакция на
  своём engine, и для новых таких записей это единственная дверь. Импорт
  `sqlalchemy` вне `infrastructure/db/` запрещён по той же причине, по которой
  репозитории возвращают доменные модели, — иначе знание о колонках расползается
  по сервисам и сценариям.
  Списки исключений — `[tool.db_access]`, проверяется
  `scripts/check_db_access.py` (в `make interface-check`).

## Events-флоу

```
Use case → event: DomainEvent
         → EventPublisher.publish(event)
         → composition/event_router.py::EventRouter.publish(event)
         → TaskQueue.enqueue(<обработчик>.__name__, ...)
```

- Новое событие: создать в `app/domain/events/`, добавить ветку в
  `composition/event_router.py`.
- Маршрутизатор САМ реализует порт `EventPublisher` — отдельной обёртки нет.
- **Публиковать только ПОСЛЕ `commit()`.** Воркер разбирает очередь мгновенно
  и своей сессией: опубликованное до фиксации читает базу раньше, чем в ней
  появится строка.
- Аргументы задачи — только именованные: провайдер арендатора очереди читает
  `message.kwargs`.
- В тестах использовать `NoopEventPublisher` (не создаёт задач Taskiq).

## Тесты

- Структура зеркалит проект: `tests/unit/app/domain/...`, `tests/integration/app/infrastructure/...`
- **Unit** (`make test-unit`): без БД/Redis/сети, дублёры только для портов, запускаются параллельно.
  Дублёр — обычный класс, а не `MagicMock`: мок принимает и тот вызов, которого
  в порту уже нет, и тест остаётся зелёным после переименования метода.
- **Integration** (`make test-integration`): PostgreSQL поднимается автоматически через testcontainers,
  прогоняет `alembic upgrade head` один раз за сессию, таблицы очищаются между тестами.
- Настройки в тестах собираются поимённо, а не читаются из `.env`: иначе
  `alembic upgrade head` и `TRUNCATE` уедут в рабочую базу разработчика.

## Конфигурация

Все настройки через env с вложением `APP__ENV`, `DATABASE__HOST` и т.д.
Окружения: `development` | `production`.

В тестах settings создаётся напрямую:
```python
Settings(app=App(...), database=Database(host=..., port=...), llm=LLM(api_key="test-key"))
```

## Логирование

`loguru`. Импортировать `from loguru import logger`. Стандартный `logging` не использовать.

## Что удалить, заводя настоящий проект

Демонстрационная сущность — `User` со сценариями регистрации, приветствия от
модели и уборки неподтверждённых. Она показывает шов через все слои: доменная
модель → порт → сценарий → событие → обработчик очереди → строка расписания.

Оставить `User` почти наверняка стоит; удалить — то, чего в проекте нет:
`welcome_message` вместе с `WelcomeUserUseCase`, `AiService` и `UserRegistered`,
если языковая модель не нужна. След ищется грепом: `rg -l welcome app tests migrations`.

Полностью общее и удалению не подлежит: сторожа в `scripts/`, конфиги в
`pyproject.toml`, `tach.toml`, композиция, точки входа, `logging.py`,
`AutonomousSession`, `KeyGuard`, реестр задач и `.claude/`.
